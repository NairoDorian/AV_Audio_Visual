# Spike P0.3: system-output capture on Windows

Status: decided for v0.1 (2026-11-07); comparison with the `wasapi` crate not run.

## Question

Can `cpal` 0.18 capture system output through WASAPI loopback well enough for Phase 1B, or do
we need the `wasapi` crate for event mode and device-position timestamps?

## What the source does (cpal 0.18.2)

- `build_input_stream` on a **render** device adds `AUDCLNT_STREAMFLAGS_LOOPBACK` in shared
  mode (`cpal src/host/wasapi/device.rs:853-856`): true loopback of the endpoint mix, no
  virtual driver.
- The callback period is the device period (`GetDevicePeriod`); the buffer duration only sets
  ring latency (same file, comment above line 853).
- `InputCallbackInfo::timestamp()` carries a capture instant (`src/timestamp.rs`), the hook for
  device-clock anchoring.
- Error kinds distinguish `DeviceChanged` (default device rerouted, stream continues) from
  `DeviceNotAvailable` (stream ended).

## Result

- `av-audio::live::LiveSource` captures the default render endpoint (loopback) and the default
  microphone through the same code path, typed f32/i16/i32/f64 to f32 in the callback with a
  scratch buffer allocated once (whole frames per push).
- Verified on Windows 11 Pro 26300: `cargo test -p av-audio -- --ignored` (loopback opens,
  delivers finite samples, stops cleanly) and `bun run tauri dev -- -- --system` (Studio shows
  live bars from the machine's playback, status "audible", DSP 52 us average in a dev build).
- Decision: **cpal for v0.1** (system output on Windows, microphone everywhere). One crate, one
  callback shape, already used by ZER0.

## Still open (not verified)

- Format matrix (s16/s32/24-in-32, 6 channels), device unplug and default-endpoint change
  recovery, 10-minute soak, callback p99: Phase 1B.2/1B.4 gates.
- Timestamps still use the sample-count clock; device-clock anchoring from the callback
  instant is next.
- Comparison with the `wasapi` crate (event mode, `pu64QPCPosition`): not run. Revisit only if
  timestamps or recovery fall short.
- macOS and Linux system output use other backends (process tap / ScreenCaptureKit, PipeWire);
  on those OSes "System audio" currently reports an error rather than silently using the mic.
